# Frontend Standards

> **Що це.** Стратегічний контракт фронтенду Future Media: технології, архітектурні межі та
> правила, порушення яких коштує інциденту. Читається за 5 хвилин, цитується в code review за ID.
>
> **Чого тут немає.** Того, як писати добре код. Це рівень **[Guidelines-Handbook](../Guidelines-Handbook/)**:
> він пояснює поняття й показує, як застосовувати рішення звідси. Конкретні реалізації —
> у **[Reference-Recipes](../Reference-Recipes/)**.
>
> Правило потрапляє на цю сторінку, лише якщо воно фіксує **технологію**, задає **архітектурну межу**
> або запобігає **інциденту**, який більше нічим не ловиться. Наслідок іншого правила — не правило.

## Як читати цей документ

| Ключове слово | Що означає під час code review |
| --- | --- |
| **MUST** / **MUST NOT** | Блокер. PR не мерджиться, доки не виправлено або не зафіксовано exception. |
| **SHOULD** / **SHOULD NOT** | Позиція за замовчуванням. Відхилення допустиме, але має бути озвучене й прийняте рев'ювером. |
| **MAY** | Явно дозволено. Це не рекомендація. |

- `[N16]` / `[N15]` — стосується лише цього мажора Next.js. `[R19]` — лише React 19.
- `†` — інструмент **ще не встановлений**; до його впровадження правило тримається лише на review.
- У колонці «Контроль» формат `пакет » правило`: зліва те, що встановлюється, справа — що вмикається.
- Усе, що автоматизується, **MUST NOT** обговорюватися в review вручну. Виправляй інструмент, не коментар.
- ID правил незмінні — і при переїзді між рівнями теж.

**Область дії.** Стосується всього нового фронтенд-коду і будь-якого файлу, який зачіпає PR.
Наявний код не переписується «за фактом виявлення». Винятки: див. [Управління стандартом](#управління-стандартом).

## Управління стандартом

**Три рівні.** `Standards/` — що вирішено (ця сторінка). `Guidelines-Handbook/` — що це означає і як
застосовувати. `Reference-Recipes/` — як це виглядає в коді. Твердження, яке потребує прикладу, щоб
його зрозуміли, не належить сюди за визначенням.

**Тест на приналежність.** Правило лишається тут, лише якщо на питання «що зламається, якщо його
прибрати?» відповідь — інша технологія, порушена архітектурна межа або інцидент. Якщо відповідь
«код стане гіршим» — це Handbook. Якщо правило є наслідком іншого правила — це Handbook.

**Винятки.** Правило можна порушити усвідомлено. Зафіксуй це в `Standards/exceptions.md`:
ID правила → причина → прийнятий trade-off → власник → **дата закінчення**. Постійних винятків
не існує; прострочені закриваються, і код або виправляється, або виняток перезатверджується.

**Зміна правила.** Відкрий PR до цього файлу з описом, яке правило змінюється і чому, плюс
потрібне оновлення Handbook. Тиждень на фідбек; затверджують власник і ще один сеньйор.

**Два неймспейси ID.** `FE-LIB-*` — рядки нормативної таблиці стеку: який інструмент обраний.
`FE-<ДОМЕН>-NN` — усе інше: як його застосовувати. Технологічний вибір змінюється лише через
`FE-LIB-*`; правило, яке просто повторює рядок таблиці, до Standards не додається.

**ID правил** незмінні — і при переїзді між рівнями теж. Виведене з обігу правило позначається
`[DEPRECATED]`, а його ID ніколи не перевикористовується, щоб коментарі в review, які на нього
посилаються, залишалися зрозумілими.

**Забезпечення виконання.** Правила з позначкою `†` є декларативними, доки не з'явиться їхній
інструмент — вони в backlog впровадження, а не тихо проігноровані. Правило, яке залишається
неавтоматизованим і неавтоматизовним два квартали, або переходить у Handbook, або видаляється.
