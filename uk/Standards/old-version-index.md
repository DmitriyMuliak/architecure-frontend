# Frontend Standards

> **Що це.** Авторитетний перелік інженерних правил для фронтенду Future Media.
> Кожен пункт — це правило, а не порада. Читається за 5 хвилин, цитується в code review за ID.
>
> **Що це не.** Це не handbook і не туторіал. Обґрунтування, патерни, приклади та анти-патерни
> живуть у **Handbook**; покрокові інструкції — у **Recipes**.
> Якщо твердження неможливо зрозуміти без прикладу — йому не місце на цій сторінці.

## Як читати цей документ

| Ключове слово               | Що означає під час code review                                                               |
| --------------------------- | -------------------------------------------------------------------------------------------- |
| **MUST** / **MUST NOT**     | Блокер. PR не мерджиться, доки не виправлено або не зафіксовано exception.                   |
| **SHOULD** / **SHOULD NOT** | Позиція за замовчуванням. Відхилення допустиме, але має бути озвучене й прийняте рев'ювером. |
| **MAY**                     | Явно дозволено. Це не рекомендація.                                                          |

**Маркери**

- `[N16]` / `[N15]` — стосується лише цього мажора Next.js. `[R19]` — лише React 19.
- `†` — інструмент **ще не встановлений**; до його впровадження правило тримається лише на review.
- Усе, що автоматизується, **MUST NOT** обговорюватися в review вручну. Виправляй інструмент, не коментар.

**Область дії.** Стосується всього нового фронтенд-коду і будь-якого файлу, який зачіпає PR.
Наявний код не переписується «за фактом виявлення». Винятки: див. [Управління стандартом](#управління-стандартом).

## 1. Технологічний стек

Core-бібліотеки не обговорюються і однакові в усіх продуктах. Нові проєкти стартують на останніх
стабільних мажорах; наявні проєкти фіксують мажор і оновлюються усвідомлено.

| Задача                               | Бібліотека                     | Примітки                                                  |
| ------------------------------------ | ------------------------------ | --------------------------------------------------------- |
| UI-фреймворк                         | React                          | 18 → 19; нові проєкти на 19                               |
| Мета-фреймворк                       | Next.js                        | **тільки App Router**                                     |
| Мова                                 | TypeScript                     | `strict`; `[N16]` потребує ≥ 5.1                          |
| Стилізація                           | Tailwind CSS v4                | CSS-first `@theme`, без `tailwind.config.js`              |
| Поведінка компонентів                | react-aria-components          | єдиний санкціонований headless-шар                        |
| Інтернаціоналізація                  | next-intl                      |                                                           |
| Runtime-валідація                    | Zod                            | `zod/mini` у пакетах, що йдуть у клієнтський бандл        |
| Unit / компонентні тести             | Vitest + React Testing Library |                                                           |
| Документація UI та interaction-тести | Storybook (+ `addon-vitest`)   |                                                           |
| Visual regression та E2E             | Playwright                     |                                                           |
| Пакетний менеджер / білд             | pnpm + Turborepo               | `packageManager` і версія Node зафіксовані в кожному репо |

| ID          | Правило                                                                                      | Контроль |
| ----------- | -------------------------------------------------------------------------------------------- | -------- |
| FE-STACK-01 | Задачу, яку вже покриває core-бібліотека, **MUST NOT** вирішувати другою бібліотекою.        | review   |
| FE-STACK-02 | Мажорні оновлення core-бібліотек **MUST** виноситись в окремий PR, ніколи не всередині фічі. | review   |
| FE-STACK-03 | `[N16]` Проєкти **MUST** працювати на Node ≥ 20.9; Node 18 не підтримується.                 | CI setup |

## Ще не вирішено

Наразі відкритих питань немає — усі рішення від 2026-08-24 перетворені на правила вище.

Це не декоративна секція. Коли виникає питання, на яке стандарт не відповідає, воно потрапляє
сюди **до того**, як хтось почне спиратися на власний дефолт. Порожній список означає «ми знаємо,
що робимо», а не «питань більше не буває».

## Управління стандартом

**Винятки.** Правило можна порушити усвідомлено. Зафіксуй це в `Standards/exceptions.md`:
ID правила → причина → прийнятий trade-off → власник → **дата закінчення**. Постійних винятків
не існує; прострочені закриваються, і код або виправляється, або виняток перезатверджується.

**Зміна правила.** Відкрий PR до цього файлу з описом, яке правило змінюється і чому, плюс
потрібне оновлення Handbook. Тиждень на фідбек; затверджують власник і ще один сеньйор.

**ID правил** незмінні. Виведене з обігу правило позначається `[DEPRECATED]`, а його ID ніколи
не перевикористовується — щоб коментарі в review, які на нього посилаються, залишалися зрозумілими.

**Забезпечення виконання.** Правила з позначкою `†` є декларативними, доки не з'явиться їхній
інструмент — вони в backlog впровадження, а не тихо проігноровані. Правило, яке залишається
неавтоматизованим і неавтоматизовним два квартали, або переходить у Handbook, або видаляється.
